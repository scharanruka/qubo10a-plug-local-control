# Qubo HSP02 Smart Plug — Reverse-Engineering Findings & Session Summary

Status date: 2026-11-02. This file is the record of everything learned and changed, for later
retrieval. Goal was: local control (stats + relay + scheduling) over BLE, no Qubo cloud/account.

---

## TL;DR

- **Stats over BLE** — works, fully local (already did before this session).
- **Relay control over BLE** — the command frame was fully reverse-engineered from the
  `com.hero.iot` APK, but it is **cloud-gated**: the relay command is AES-128 encrypted with a
  per-device `securityKey` that Qubo's cloud generates during commissioning. It cannot be derived
  or reset locally. The stock firmware **cannot** do no-account local relay control.
- **The real path to fully-local relay control** is **ESPHome** (replace the firmware on the
  ESP32). Pin map in `AGENTS.md`.
- **Reconnect/restart bug** — fixed (root cause + code + systemd path).

## 1. Reconnect / restart bug (FIXED)

Two separate causes, both fixed:

1. **Stale bond → auth failure.** The plug's BLE key regenerates when *it* reboots, but BlueZ
   kept the old bond, so every connect failed with
   `LE.Disconnected - Reason.Authentication`. The plug doesn't need bonding at all (reads work
   unencrypted). Fix in `qubo_poller.py`: detect any leftover bond, `RemoveDevice`, rediscover,
   connect unencrypted; never pair again.
2. **Stale systemd path.** The user unit pointed at
   `/home/scharanruka/dev/hardware/qubo10a-plug-firmware` (moved away); it now points at this
   workspace. Fix in `/home/scharanruka/.config/systemd/user/qubo-poller.service`.

Also added: auto-discovery if the plug isn't yet in BlueZ's device cache (e.g. right after a
reboot).

## 2. The relay command — fully cracked

Reverse-engineered from `base.apk` (version 3.3.42 / versionCode 742, `com.hero.iot`, 13475
classes) using REA + JADX (`jadx-headless-mcp 0.7.1`) plus hand-written dex parsers.

### GATT map (exact, from `AppConstants`)

| AppConstants field | UUID | meaning |
| --- | --- | --- |
| `WIFI_BULB_READ_SERVICE` | `000000dd-0000-1000-8000-00805f9b34fb` | service: telemetry + relay |
| `WIFI_BULB_SW_VER_SERVICE_READ` | `0000dd01-…` | model string (`HSP02_01_01_14_SYSTEM-10A`) |
| `WIFI_BULB_COLOR_SERVICE_READ` | `0000dd02-…` | **relay state (read) + relay command (write)** |
| `WIFI_BULB_STATE_SERVICE_READ` | `0000dd03-…` | vendor status (`S_06`, `\x00\x00\x00\x00` after reset) |
| `WIFI_PLUG_POWER_CONSUMPTION_SERVICE_READ` | `0000dd04-…` | live telemetry CSV (mA,V,W,counter,Wh) |
| `WIFI_BULB_CUSTOM_SERVICE` | `000000ee-…` | commissioning service |
| `WIFI_BULB_CUSTOM_SERVICE_WRITE` | `0000ee01-…` | commissioning write (setup + `sk`) |

### Relay command construction (write to `dd02`)

```
payload = {"data":"<HEX>"}                        (UTF-8 bytes, written to dd02)
  <HEX> = uppercase hex of AES-128-ECB-NoPadding(key, plaintext)
  plaintext = {"command":{"devices":{"services":{"lcSwitchControl":{"instanceId":0,"attributes":{"power":"on|off"}}}}}}
             padded with trailing spaces to a multiple of 16 bytes
  key = the plug's per-device `securityKey` (16 ASCII bytes, used directly as AES-128 key)
```

- Service name is **`lcSwitchControl`**, attribute **`power`**, value **`on`/`off`** (not `1`/`0`).
- The BLE write uses a *different, shorter* format than the cloud command (the app's
  `control_bt_lccommand` resource — no `handleName`/`deviceUUID`).
- Encryption verified byte-for-byte against `openssl enc -aes-128-ecb`.
- Long writes are **split/chunked** by the app (MTU-3 sized pieces, via `e3.a` → `f3.d`).

### Key classes in the APK (mostly R8-obfuscated)

| class | role |
| --- | --- |
| `com.hero.iot.utils.AppConstants` | UUID + key constants (`BLE_KEY`, `SUBSCRIBER_ID`) |
| `Ab.n0` | command dispatcher (`n0.r().A(...)` builds/encrypts/sends) |
| `Ab.a` | AES crypto (`AES/ECB/NoPadding`, `SecretKeySpec(key.getBytes(),"AES")`) |
| `k3.c` | byte→uppercase-hex codec |
| `e3.a` | BLE GATT manager (singleton `.k()`; `L(...)` = write) |
| `f3.d` | split/chunked long write |
| `h3.b` / `Fb.a` | BLE device model / parcelable wrapper |
| `com.hero.iot.ui.dashboard...smart_plug.SmartPulgDashboardFragment` | plug UI; `onPlugCommand` = relay toggle |
| `com.hero.iot.ui.commissioning.blehub.BleApplianceCommissionActivity` | commissioning; `za()` = the write |

### Key provisioning (the cloud gate)

- The relay key = `securityKey`, a device attribute in Qubo's cloud.
- During commissioning the app writes (plaintext, to `ee01`):

  ```json
  {"sk":"<HEX>", "a":1, "s":"<SSID>", "p":"<pass>",
   "duid":"<deviceUUID>", "spid":"d10e4bfb0153496e8e8bb955f7ebe413",
   "atok":"<accessToken>", "rtok":"<refreshToken>", ...}
  ```

  where `sk = uppercase-hex(AES-128-ECB("NdRgUkXp2s5vByAD", securityKey))`.

- `bleSecurityKey`/`securityKey` is **generated by the cloud** during commissioning and returned to
  the app; the app only passes it through. `AppConstants.BLE_KEY = "ABCDEFGHIJKLMNOP"` is a
  fallback the app uses when the cloud didn't issue a key.

### Why local relay is impossible with stock firmware (the finding)

Tested exhaustively against the live plug (after a factory reset): the default key
`"ABCDEFGHIJKLMNOP"`, and re-provisioning a known key via the commissioning write (`ee01`), in
every combination — minimal/full JSON, plain/chunked writes. Every write is ATT-acknowledged but
**silently ignored**; `dd02` never flips. Conclusion: the relay command only works on an
*already-cloud-commissioned* plug, and the key can only be obtained from the cloud. No account ⇒
no local relay on stock firmware.

## 6. The Wi-Fi route — evaluated and rejected (2026-11-03)

**Verdict: Wi-Fi does not give local control on stock firmware. It is a cloud tether, not an API.**

Evidence:

- **LAN scan from the wired PC** (`192.168.29.0/24`, full ICMP sweep + neighbour table): live hosts are the
  router `192.168.29.1` and this PC; the only other MACs are phones with randomised addresses
  (`be:77:46:…`, `a4:ae:12:…`, `60:35:73:…`). **No Espressif OUI `3C:0F:02` anywhere.** Expected: the plug
  was factory reset, which wipes Wi-Fi credentials, so it is BLE-only until re-commissioned.
- **APK has no local control path.** All device traffic is vendor cloud:
  `mqtt.platform.quboworld.com:8883` (MQTT over TLS, the device uplink), `srvcapp.platform.quboworld.com:443`
  (REST), `stun6.platform.quboworld.com:5349` (WebRTC, cameras only). No mDNS/Bonjour, no CoAP, no SSDP, no
  UDP discovery, no "device IP + HTTP" code, no `_tcp` service type for appliances. The app cannot talk to a
  plug over the LAN because it never learned how.
- Device credentials are per-device cloud-issued, same shape as the BLE gate: `mqttPassword` and
  `device_access_token` are pulled from the cloud into the app DB at commissioning.

Consequence: the AES `securityKey` gate is BLE-specific, but the Wi-Fi path is **account-gated instead**.
Wi-Fi changes the transport, not the wall. Traffic is TLS to the vendor broker, so impersonating it needs a
trusted cert on the plug — more work than ESPHome, and it yields nothing BLE cannot already do.

Only Wi-Fi thing still worth one minute of user time: after a reset, look for a new SSID near the plug
(`Qubo…`, `AYLA…`, `ESP…`). A SoftAP + `192.168.4.1` config page would be a genuinely unauthenticated local
endpoint. The app commissions over BLE (`BleApplianceCommissionActivity`), so a SoftAP is unlikely.

## 7. BLE relay — exact frame recovered from code (2026-11-04)

The "cloud-gated / writes silently ignored" conclusion in §2 was a **measurement error**, not a
firmware property. We were sending a frame the plug never had a reason to parse. Evidence below is
from `base.apk` (`sha256 524dd6…60c8`, v3.3.42/742) via REA + JADX.

### The app's BLE command path (call chain, decompiled)

```
Ab.n0.A(device, service, attribute, value, instanceId, …)      // generic command
  └ getString(R.string.control_bt_* template)  → inner JSON   // no handleName, no deviceUUID
  └ new JSONObject().put("command", innerJson)                // outer wrapper
  └ new Ab.a(Ab.n0.k(device)).a(plainJson)                     // AES-128-ECB → hex
  └ new JSONObject().put("data", hex)                          // {"data":"…"}
  └ Ab.n0.I(dev, WIFI_BULB_READ_SERVICE, WIFI_BULB_COLOR_SERVICE_READ, bytes)
      └ e3.a.L(b, svc, char, bytes, cb) → M(…, split=true) → N(…)
          └ if (bytes.length > 20 && split)  new f3.d().l(...)  // SPLIT WRITE
```

### The five things we got wrong

| # | App does | We did | Effect |
| --- | --- | --- | --- |
| 1 | inner JSON has **no** `handleName` / `deviceUUID` | sent the cloud template with both | parser sees unknown shape |
| 2 | hex is **lowercase** (`k3.c.c` → `d(bytes,true)` → `e(bytes, f54630a)` = `0-9a-f`) | `.upper()` | wrong-frame (or wrong-key) either way |
| 3 | payload written in **chunks of `r()` bytes** (`f3.d.j` = plain sequential slices, no header, no CRC, no length byte) | one 332-byte `WriteValue` | BlueZ falls back to a Prepare/Execute *long write*; the plug's handler never got a complete un-chunked frame |
| 4 | `e3.a.r()` = MTU, split only when `len > 20`, chunks written with response, next chunk triggered by the write callback | not chunked at all | same as 3 |
| 5 | key = device attribute `serviceName="securityKey"`, `attributeName="securityKey"` (case-insensitive), else `AppConstants.BLE_KEY="ABCDEFGHIJKLMNOP"` | assumed a `bleHub` service | key lookup was aimed at a service that does not exist |

Note `Ab.n0.k()`: the fallback key is used when that attribute is empty. So an un-commissioned plug
is *expected* to accept `ABCDEFGHIJKLMNOP` — which is exactly the state our plug is in.

### Correct frame (what a working write looks like)

```
plaintext = {"command":{"devices":{"services":{"lcSwitchControl":{"instanceId":0,"attributes":{"power":"on"}}}}}}
            (padded with trailing spaces to a multiple of 16)
hex       = lowercase( AES-128-ECB-NoPadding( securityKey , plaintext ) )
frame     = {"data":"<hex>"}                                   (UTF-8 bytes)
write     = dd02, chunked into r() byte pieces, sequentially, each write-with-response
```

`{R.string.control_bt_commands}` (the 4-arg form used by `Ab.n0.A` →
`{"devices":{"services":{"%1$s":{"instanceId":%2$d,"attributes":{"%3$s":%4$s}}}}}`) matches this
exactly, with the value pre-quoted because the template does not quote it.

### Files

- `qubo_poller.py` — `build_relay_payload()` now builds the short template + lowercase hex;
  `Plug.write_chunked()` writes in MTU-sized pieces with verification.

### Commissioning route (ee01) — tested, no effect on a factory-reset plug

Recovered `BleApplianceCommissionActivity.za()`: the frame written to `ee01` is **plaintext JSON**
(`Ab.a.b("NdRgUkXp2s5vByAD", securityKey)` encrypts only the `sk` field), fields:
`sk, a=1, s(ssid), p(password), lduid, guid, duid, euid, spid=d10e4bfb0153496e8e8bb955f7ebe413,
uuid, murl, hurl, ourl, ota-token, atok, rtok, rc`. Write path is the same chunked `e3.a.L`.
The securityKey itself is **cloud-generated** (`za` gets `bleSecurityKey` from the cloud sync event),
so a fully offline commissioning needs a self-chosen key.

Implemented in `research/provision.py`. Results on the reset plug, chunk sizes 0/20/244:

| Probe | dd02 | dd03 |
| --- | --- | --- |
| before | `1` | `\0\0\0\0` |
| after provisioning frame (dummy SSID) | `1` | `\0\0\0\0` |
| relay frame with the installed key | `1` | — |

GATT tree is as expected: `dd02` read/write/notify, `ee01` write-only, unique paths, no errors on
either write. Bonding (`bluetoothctl pair`, Just Works) changes nothing.

Open question: the plug's original `dd03` value was `S_06`; it now reads four zero bytes. If `dd03` is
the vendor status field, the plug's control task may be stalled (GATT server alive, command handler
not), which would explain why *every* frame — correct or not — is ignored.

### The gate is the plug's state, not the frame

`dd03` is the plug's **status code**, read live:

| dd03 | meaning |
| --- | --- |
| `S_01` | pairing / commissioning mode (accepts `ee01`) |
| `S_06` | normal operation (original, cloud-provisioned state) |
| `\0\0\0\0` | seen after the reset, before the button test |

Sequence that proved it (plug in `S_01`, i.e. LED blinking fast):

1. Wrote the `za()` provisioning frame to `ee01` with a dummy SSID → plug **dropped the BLE link**
   within 2 s to try joining Wi-Fi. So the frame is parsed and accepted.
2. Join failed (no such network) → plug rebooted back to `S_01`.
3. Relay frame with the key we installed → still ignored.

Conclusion: the plug **only commits `securityKey` after a successful Wi-Fi join**, and the
pre-existing key (from its original commissioning) survives both factory reset and our
provisioning attempts, so every relay frame we send fails authentication.

Nine combinations on `dd02` (key = `ABCDEFGHIJKLMNOP` / the `NdRgUkXp2s5vByAD` KDF key ×
lower/upper hex × `{"data":…}` wrapper / bare hex / plaintext JSON), plus double-send: **all ignored**.
Frame shape is not the variable; the key is.

Next: provisioning frame in `S_01` with a **real** 2.4 GHz SSID/password (phone hotspot is fine),
which lets the join succeed and the plug commit the key we chose.

### dd03 error codes (first observations)

| dd03 | meaning |
| --- | --- |
| `S_01` | pairing mode — accepts `ee01` frames |
| `S_06` | normal (original cloud-provisioned state) |
| `E_05` | Wi-Fi connect failed (seen with both the real hotspot SSID and a nonsense SSID) |
| `\0\0\0\0` | early/reset state |

Behaviour confirmed by measurement: in `S_01` the plug **drops the BLE link ~3 s after** a valid
provisioning frame (it reboots) and later reports `S_01` or `E_05`; in `E_05` writes are ignored and
the link stays up. So each provisioning attempt needs a button hold back into `S_01`.

Filling `murl`/`hurl` with the real values from `c6.a.<clinit>`
(`mqtt.platform.quboworld.com:8883`, `srvc.platform.quboworld.com:443`) did **not** change the
outcome, so the missing URLs were not the gate.

## 8. SOLVED — local relay control, no cloud account (2026-11-04)

**The frame was never the problem. The plug's stored key was.** A factory reset does not clear
`securityKey`, and the plug only replaces it when it is given a provisioning frame *and successfully
joins Wi-Fi*.

### What finally worked

1. Hold the plug's power button ~10 s → LED blinks fast, `dd03` = `S_01`.
2. Write the `ee01` provisioning frame from `research/provision.py` with:
   `sk = hex(AES-ECB("NdRgUkXp2s5vByAD", "ABCDEFGHIJKLMNOP"))`, `a=1`, real 2.4 GHz SSID/password,
   `spid=d10e4bfb0153496e8e8bb955f7ebe413`, `murl`/`hurl` from `c6.a.<clinit>`, empty tokens.
3. The plug drops the BLE link ~3 s later (reboots to join Wi-Fi). On a successful join the key is
   committed; it then reports `E_05` because the empty `atok`/`rtok` cannot authenticate to Qubo cloud.
4. Relay frames on `dd02` with `ABCDEFGHIJKLMNOP` now work: **5/5 toggles**, `ON`/`OFF` verified from
   the appliance itself, and the key survives a power cycle (`f4` counter restarted, control still fine).

### Verified behaviour

| Observation | Detail |
| --- | --- |
| `dd02` | `1`/`0`, follows commands; also follows the physical button |
| `dd04` | CSV only while the relay is **on**; bare `'0'` when the relay is off |
| link after a relay command | may drop for a few seconds while the plug applies it |
| `dd03` | `S_01` pairing, `S_06` normal, `E_05` Wi-Fi/cloud failure |
| `f4`/`f5` | reset to `0` by provisioning — another reason the poller integrates energy itself |

### Changes to `qubo_poller.py`

- `build_relay_payload()` — app-exact frame (short template, lowercase hex, compact JSON).
- `Plug.write(..., chunk=20)` — sequential chunked writes (the app splits at the MTU).
- `sample()` — bare `'0'` from `dd04` means "relay off, 0 W", not a corrupt frame.
- relay loop — trusts the command it just sent instead of reading `dd02` back (the link may be gone).
- `--relay on|off` / `--chunk N` for one-shot testing.

### Files

- `research/provision.py` — builds and sends the provisioning frame, then retests the relay.
- `research/relay_matrix.py` — the negative matrix that ruled out frame shape (kept as evidence).

### Stability note

Provisioning reboots the plug, which invalidates the Just-Works bond made earlier. With the stale bond in
BlueZ the link dropped every ~1-2 min (`Not connected` → reconnect). After
`bluetoothctl remove 3C:0F:02:27:CA:4A` and connecting unbonded: **0 reconnect errors in 5 minutes**, and
relay commands still work. Bonding is not needed at all.

### Hotspot off — measured (user's choice: leave it off)

| | hotspot on | hotspot off |
| --- | --- | --- |
| relay control | works | works (`dd02` 1→0→1, key still valid) |
| `dd03` | `E_05` | `\0\0\0\0` |
| BLE link | 0 drops / 5 min | drops every ~30 s, back in ~5 s |
| relay state | persists | persists (no reboot) |

So Wi-Fi is not required for control. The plug just retries its (now absent) Wi-Fi and drops BLE during
each attempt. The 5 s gaps are under the energy-integrator's 3x-interval cutoff, so kWh stays correct.

### Home Assistant gotchas found while wiring the switch

- A **stale retained discovery topic** from an earlier version (`homeassistant/binary_sensor/<node>/relay/config`)
  reused the same `unique_id` as the new switch, so HA refused the switch. Clear it with
  `mosquitto_pub -t '<topic>' -r -n`, then restart the poller to republish.
- `value_template` must not return the literal string `'unknown'` for a numeric sensor — HA logs
  `Value error ... non-numeric value: 'unknown'` on every publish. A JSON `null` renders as `"None"`,
  which HA's MQTT sensor maps to `PAYLOAD_NONE` → a real unknown state with no error. Fixed.

### "I have to toggle it several times" — fixed

Two separate causes, both from the 30 s Wi-Fi-retry churn:

1. A command that landed inside a 5 s BLE gap was **dropped** (the queue item was consumed, the write
   raised, and nothing retried). Now the desired state is kept and retried on the next cycle, so a
   toggle always lands; the latest command wins if several arrive in one cycle.
2. HA only changes the switch when we publish, which could be up to 5 s later, so the UI snapped back.
   The MQTT `on_message` now echoes the requested relay state immediately from a cached snapshot; the
   loop confirms it on the next successful read.

Measured: ON then OFF 1 s apart → final relay `0` (last command wins); state reflects a command within 2 s.
